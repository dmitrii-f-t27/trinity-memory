# Аудит: хранение тернарных весов

Проверено 2026-09-08. Исходная записка `trinity-ternary-memory.md` рассматривается как исследовательский материал. Её предположения, задачи и рекламные формулировки не являются результатами этого проекта.

Первая реализация ограничена кодеками, проверкой их обратимости и RTL-декодерами. Обучение модели, качество ответов, работа на AX7203, частота, мощность и tokens/s требуют отдельных экспериментов. Результаты других авторов ниже принадлежат их работам.

## Точное сравнение упаковки

Для произвольного блока из `n` тритов нужно различать `3^n` состояний. Минимальная фиксированная длина двоичного кода равна `b = ceil(log2(3^n))`. Для воспроизводимого целочисленного расчёта в Python: `(3**n - 1).bit_length()`.

| Тритов `n` | Бит `b` | `b/n`, плотный поток | Если каждый блок отдельно дополнен до байта |
| --- | --- | --- | --- |
| 5 | 8 | 1.600000 | 1.600000 |
| 17 | 27 | 1.588235 | `32/17 = 1.882353` |
| 22 | 35 | 1.590909 | `40/22 = 1.818182` |
| 40 | 64 | 1.600000 | 1.600000 |
| 111 | 176 | 1.585586 | 1.585586 |

Все значения в таблице вычисляются из приведённой формулы. Для отдельно выделенного 36-битного BRAM-слова с 22 тритами фактически занято `36/22 = 1.636364 bpw`, даже если один бит используется для контроля чётности. Упаковка `17 + 5` тритов занимает `27 + 8 = 35` информационных бит; выражение `27 + 9 = 36` включает дополнительный бит. Расчёт плотного потока не учитывает заголовки, выравнивание, scale, DMA-передачи и занятую ёмкость физических блоков памяти.

При наличии общего FP16 scale на каждые `g` весов его амортизированная цена составляет `16/g bpw` для полных групп. Метаданные и последние неполные группы следует считать по реально записанным байтам. Сравнение TQ-форматов по целым блокам: экономия `1 − 54/66 = 18.1818%`, идеальное отношение пропускной способности `66/54 = 1.2222`. Это отличается от сравнения чистых payload `2.0` и `1.6`.

## Разреженность: контракт кодека и качество модели

Здесь используем явное обозначение `(block_size, max_nonzero)`. Количество допустимых состояний:

```text
states(N, K) = sum(comb(N, j) * 2**j for j in range(K + 1))
code_bits   = ceil(log2(states(N, K)))
```

Формула выбирает `j` ненулевых позиций и один из двух знаков в каждой; нулевой блок включён. Поэтому `(4,1)` даёт `1 + 4×2 = 9` состояний, а `(8,2)` — `1 + 8×2 + 28×4 = 129`. Это согласуется с [Table I работы 2017 года](https://arxiv.org/html/1707.03684v1#S2).

Для **ровно** двух ненулевых в восьми позициях состояний было бы `28×4 = 112`, что помещается в семь бит. Но этот другой контракт не кодирует блоки с нулём или одним ненулевым. Для **не более** шести ненулевых в восьми позициях состояний 5281, нужно 13 бит: `1.625 bpw`. Нельзя переносить стоимость кодирования `(8,2)` на Sparse-BitNet `6:8`.

Для независимых тритов с долей нулей `p0` и равными вероятностями знаков энтропия равна:

```text
H = -p0*log2(p0) - (1-p0)*log2((1-p0)/2)
```

Подстановка `p0 = 1/3, 0.4, 0.6, 0.75, 0.85` даёт соответственно `1.584963, 1.570951, 1.370951, 1.061278, 0.759840` бит/вес. Это теоретическая средняя энтропия при указанных предпосылках, не размер файла. Структурные ограничения создают зависимости между соседями, поэтому блочный код может оказаться плотнее энтропии, вычисленной только из общей доли нулей.

Кодек обязан отклонять вход, не удовлетворяющий своему ограничению. Принудительное обнуление лишних весов — отдельная операция pruning, которая меняет модель. Тест обратимости кодека не доказывает сохранение perplexity или качества после pruning. [Sparse-BitNet](https://arxiv.org/html/2603.05168v1#S3) оценивает качество для конкретных моделей и режимов обучения; [работа 2017 года](https://arxiv.org/html/1707.03684v1#S3) — для своих DNN/CNN, не для этого прототипа.

## Ограничения обзора и следующего эксперимента

- Страница KVTQ на [OpenReview](https://openreview.net/forum?id=eZAlb8fX5y) потребовала browser verification. Самостоятельно проверить полный текст и историю её публикации не удалось: **я не могу это подтвердить**. Доступная работа [2608.03229, reference 27](https://arxiv.org/html/2608.03229v1#bib.bib35) ссылается на KVTQ как на работу 2023 года, submitted to ICLR 2024; это вторичное свидетельство о KVTQ, не проверка статуса принятия.
- Производительность из ICS 2026, численные заявления о QMoE, KIVI, TurboQuant, BitNet a4.8 и физических SRAM/NVM-ячейках не проходили полный аудит в этой первой итерации и не используются как результаты проекта. Для них **я не могу подтвердить все числа исходной записки**.
- Полный перебор малых кодовых пространств и сравнение программного и RTL-декодирования дают свидетельства логической корректности. Измерение времени Python-кодека характеризует конкретную программную реализацию на конкретном компьютере.
- Для аппаратного результата нужны одна версия Vivado, точно указанный FPGA part, одинаковые ограничения и интерфейсы для baseline и packed-варианта; отчёты LUT/FF/BRAM, timing после route и эксперимент на устройстве. Полосу DDR и tokens/s следует измерять на полном тракте с декодированием и вычислениями.
- Для качества нужны checkpoint и его лицензия, воспроизводимые данные, seed, QAT/pruning-конфигурация и оценка до/после. Для публикации о новом методе нужно сформулировать отличие от уже существующих TerEffic, структурного кодирования и signed-digit KV.

Источники открыты через BrowserOS neo. AMD DS180 — спецификация версии 2.6.1 от 2020-09-08 для рассматриваемого поколения FPGA; она использована для свойств LUT и конфигурации, а не как источник актуальных цен или доступности оборудования.
